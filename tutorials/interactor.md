# Interactor Writing Guide (testlib.h)

Reference: https://codeforces.com/blog/entry/18455

## What is an interactor?

An interactor is a special judge program for **interactive problems** — problems where the participant's solution communicates back-and-forth with the judge during execution. The participant queries the interactor and receives answers, then eventually outputs a final result.

Examples: binary search problems where you can ask "is X > Y?", guessing games, adaptive input problems.

## Registration

```cpp
#include "testlib.h"
using namespace std;

int main(int argc, char* argv[]) {
    registerInteraction(argc, argv);
    // ...
}
```

`registerInteraction` is mandatory. It sets up the four I/O streams.

## The four streams

| Stream | Direction | Purpose |
|--------|-----------|---------|
| `inf`  | interactor reads | Test input file (generated by generator) |
| `ouf`  | interactor reads | What the **participant outputs** (their queries) |
| `ans`  | interactor reads | Answer file (rarely used in interactive) |
| `cout` | interactor writes | What the **participant receives** (your responses) |

**Never** read participant output from `cin`. Always use `ouf`.  
**Always** write responses via `cout` (or `tout` for the log).

## Critical: flushing

Every response written to `cout` **must be flushed immediately** — otherwise the participant blocks waiting for input that never arrives.

```cpp
cout << response << "\n";
cout.flush();   // or use endl which flushes automatically
```

Using `endl` instead of `"\n"` is safe but slower. For interactive problems, correctness > speed here.

## Verdict functions

```cpp
quitf(_ok, "correct in %d queries", queries);      // AC
quitf(_wa, "wrong answer: expected %d, got %d", expected, got);  // WA
quitf(_pe, "expected integer, got '%s'", token.c_str());         // PE
quitf(_fail, "interactor bug: %s", msg);           // judge error (not participant's fault)
```

Use `_fail` when the test data itself is wrong or the interactor has a bug — it signals a problem with the problem, not the participant.

## Reading participant output safely

Always use `ouf.read*()` with bounds so malformed output gives WA, not a crash:

```cpp
int q = ouf.readInt(1, MAX_QUERIES, "query type");   // enforces range
string token = ouf.readToken();                       // reads next whitespace-delimited token
long long x = ouf.readLong(1LL, n, "query value");
```

If `ouf.read*()` fails (out of range, wrong type), testlib automatically gives WA/PE — you don't need to handle it manually.

## Typical interactor structure

```cpp
#include "testlib.h"
using namespace std;

int main(int argc, char* argv[]) {
    registerInteraction(argc, argv);

    // 1. Read test data
    int n = inf.readInt();
    int secret = inf.readInt();

    int maxQueries = 30;
    int queries = 0;

    // 2. Interaction loop
    while (true) {
        // Read participant's next action
        string type = ouf.readToken();

        if (type == "!") {
            // Final answer
            int answer = ouf.readInt(1, n, "final answer");
            if (answer == secret)
                quitf(_ok, "correct answer in %d queries", queries);
            else
                quitf(_wa, "wrong answer: expected %d, got %d", secret, answer);
        } else if (type == "?") {
            // Query
            if (queries >= maxQueries)
                quitf(_wa, "too many queries: used %d, limit %d", queries + 1, maxQueries);
            queries++;

            int x = ouf.readInt(1, n, "query value");
            if (x < secret)
                cout << ">" << "\n";
            else if (x > secret)
                cout << "<" << "\n";
            else
                cout << "=" << "\n";
            cout.flush();
        } else {
            quitf(_pe, "expected '?' or '!', got '%s'", type.c_str());
        }
    }
}
```

## Query-count enforcement

Two valid approaches:

**Approach A — interactor enforces it:**
```cpp
if (queries >= maxQueries)
    quitf(_wa, "query limit exceeded");
```

**Approach B — read limit from test data:**
```cpp
int maxQueries = inf.readInt();  // generator writes the limit per test
```

Approach B is more flexible for problems with varying limits per test.

## Multi-test interactive problems

If the problem has T test cases, the interactor must **send `t` to the solution** after reading it from `inf`, then loop and call `setTestCase` at the start of each iteration:

```cpp
int t = inf.readInt();
cout << t << "\n";   // send t to solution — solution reads t from its stdin
cout.flush();

for (int tc = 0; tc < t; tc++) {
    setTestCase(tc + 1);  // required — testlib warns if omitted for multi-test
    int n = inf.readInt();
    // ... one full interaction per test case
    // After each test: participant outputs "!", interactor reads it and continues
}
quitf(_ok, "all %d test cases solved", t);
```

**Critical:** if the interactor does not send `t`, the solution blocks on `cin >> t` and the process deadlocks → CRASHED / exit -1 in Polygon.

The participant must flush after their answer for each test case.

## Partial scoring

For problems with partial points:

```cpp
double score = (double)correctAnswers / totalQueries;
quitf(_points, score, "solved %d/%d", correctAnswers, total);
```

Score must be in [0.0, 1.0].

## Logging with tout

Write extra diagnostic info to the checker log (visible to problem setters, not participants):

```cpp
tout << "test case: secret=" << secret << " queries_used=" << queries << "\n";
```

## Statement conventions for interactive problems

The problem statement **must** include:
- Clear query format: exact syntax the participant must print
- Final answer format: exact syntax for submitting the answer
- Query limit: maximum number of queries allowed
- Flush reminder: explicitly tell participants to flush after each line of output
- Interaction example: a sample interaction showing the back-and-forth

Example statement note:
> After printing each query, do not forget to flush the output. Use `cout << endl` (C++) or `sys.stdout.flush()` (Python).

## Polygon setup

1. In Polygon → Problem Settings → check **"Interactive"**
2. Upload `interactor.cpp` as the interactor file
3. The checker is **not** used for interactive problems — the interactor issues the verdict
4. The generator still produces test input files read by `inf`
5. The validator still validates the test input format

## Common mistakes

| Mistake | Fix |
|---------|-----|
| Not flushing after each response | Add `cout.flush()` or use `endl` |
| Reading participant output from `cin` | Use `ouf.readInt()` / `ouf.readToken()` |
| Using `quitf(_ok, ...)` before reading the final answer | Always read and validate the answer first |
| Forgetting to handle EOF (participant exits early) | `ouf.readToken()` will produce PE automatically |
| Using `_fail` for participant mistakes | Use `_wa` or `_pe` for participant errors; `_fail` is for judge bugs |
| Interactor crashes on bad input | Use `ouf.read*()` with range — it handles bad input gracefully |
